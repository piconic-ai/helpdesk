## ブラウザでの再確認

各場面を独立したローカル Worker、D1、R2、Queues と Chromium で実行しました。利用者の入力から運営者の受信箱まで同じデータを追っています。外部のメール配送、Workers AI、GitHub、通知 Webhook はローカルで応答します。J8 は起票前の確認から、スケジュール実行が Issue の終了を検出し、その下書きを人が承認するところまで確認します。

[場面別の画像と回数](index.html) の回数は、画像を記録したブラウザでのクリック、入力・選択の確定、Tab・Enter・Escape を数えたものです。別タブでの操作を含みます。ページの再取得、外部メールの到着、シード投入は含みません。

| 場面 | 歩いて気づいた点と確認したこと |
| --- | --- |
| J1 | 担当者ボタンの読み上げ名を見える文言に合わせた。担当とラベルを変えた後、返信プレビューから次の未対応に進める。 |

## 補足の場面と判断

- 公開ヘルプ・チャット・フィードバック・問い合わせフォームを、運営者の案内から顧客の受付完了まで確認した。フィードバックと返信先が必要な問い合わせでは、顧客のブラウザに保存した連絡先を自動入力した。ID やメールの手入力を禁止する検査の対象は運営画面である。
- 新着と同じ会話への返事は実際のメールハンドラーに RFC メールを渡し、R2 とキューから一覧に現れるまで待った。
- 無効な拡張を管理画面から有効にし、各案内へ移動した。定型文から作った下書きも承認待ちの件数に含め、スヌーズの設定・解除と、同じ顧客・窓口の問い合わせへの統合を確認した。統合元に残ったラベルが外せない問題を見つけ、統合グループの対象ラベルだけをまとめて外せるようにした。スヌーズの時刻は、入力時と結果のタイムゾーンを日本時間に揃えた。
- 振り分け条件を管理画面で選び、実際に届いたメールのラベルと通知を確認。認証失敗を含む別のメールは迷惑メールの一覧に移った。
- 管理画面で発行したトークンを CLI と MCP に渡した。CLI の一覧取得と MCP の下書き作成の後、運営画面で承認待ちを確認した。トークンを表示した画面は撮影していない。
- 375px でキーボードだけで返信から完了まで実行した。権限変更・表示名の保存、不正な窓口の入力エラー、最後の管理者を残す案内、削除確認を確認した。
- 既にデプロイ設定で指定した受付ポリシーと Turnstile を優先する。管理者が開始する同一サイトの受付は、そのサイトの HTML フォームに限定する。本番のアクセス制御・実在の相手への配信確認はこのローカル検証の対象外である。

## 検証結果

A1〜A7 と B1〜B13 の全20件を反映した。J1〜J11 と補足の操作を含むブラウザーテスト23件、画面比較・キーボード操作のテスト50件が成功した。アクセシビリティは49画面を3種類の幅で検査した。操作記録には、実際に表示した52枚の画像を収録している。

回帰テストは231件が成功し、分岐カバレッジは69.05%だった。全拡張を有効・無効にした受け入れテストは各64件が成功した。整形、型検査、文書検査、ビルド、Worker のドライランも通過した。関数の認知的複雑度の最大値は15だった。

## 再現

`pnpm build` の後に `pnpm test:ux` を実行する。画面を再記録するには `HELPDESK_UX_REPORT=1 pnpm test:ux`、続いて `node tests/ux/report.mjs` を実行する。ブラウザは `pnpm exec playwright install chromium` で導入できる。
