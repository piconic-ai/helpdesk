# F06 問い合わせを GitHub issue につなぐ

## 利用場面

運営者が問い合わせの原因を調べ、開発チームで直すための issue を作ります。同じ原因を報告した相手には、修正後に個別に返信できます。

## 得られる結果

会話から GitHub issue を開き、その issue に紐づく会話を一覧できます。issue が閉じたあとは、運営者が各相手への返信案を確認できます。

## 体験の流れ

1. 運営者はプロダクトのリポジトリを設定し、会話の画面で公開してよい要約を入力します。
2. 投稿されるタイトルと本文を読み、内容を確認して起票します。既存の issue がある場合はその番号を入力し、問い合わせ番号をリンクにしたコメントを投稿します。
3. 定期処理が GitHub での完了を検出すると、各会話に返信の下書きが現れます。

## 作る範囲

確認済みの要約を使う起票、既存 issue への紐づけ、両方向への参照、完了を知らせる下書きの作成を含みます。

## 作らないこと

起票前の本文の自動要約や、自動での対外返信は対象外です。

## 受け入れ条件

- **F06-AC1** GitHub には、運営者がプレビューで確認した要約と問い合わせ番号だけが投稿される。
- **F06-AC2** 同じ issue に複数の会話を紐づけられ、会話から issue、issue の紐づけ一覧から各会話を開ける。
- **F06-AC3** GitHub で issue が閉じると、各会話に承認待ちの返信案が1件でき、再配送でも増えない。

- **F06-AC4** 修正前後の期間で、同じ issue に紐付いた会話数とプロダクト全体に占める割合を「目安」として確認できる。

## 未決事項

実際の GitHub リポジトリへの起票とアクセストークンの権限は、運営者が本番設定時に確認します。
