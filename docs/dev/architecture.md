# 実装方針

単一の Worker が HTTP、メール、キュー、定期処理を受け付けます。会話の判断に必要なデータを読み出し、純粋関数が次の状態を決め、D1 の batch で会話と出来事を書き込みます。メールの原文と添付は非公開の R2 に置きます。

操作は名前、スキーマ、権限、手続きの組で登録します。運営画面と外部のクライアントは同じ操作を呼びます。拡張は静的に登録し、核のテーブルへの書き込みは核の手続きを通します。

[層ごとの依存規則と状態の定義](../plan/03-design.md)・[拡張の契約](../plan/stage-2-extension-points.md)

## プロジェクトの権限

運営者の全体の役割とプロジェクトごとの役割は別々に保存します。Access のログインでメールアドレスを検証し、招待と一致した所属を登録します。純粋関数 `can(actor, action, productId)` が閲覧、会話の操作、プロジェクトの管理、全体の管理の可否と理由を返します。

会話番号や添付の指定から実際の所属プロジェクトを引いて権限を判定します。一覧・検索・集計は、件数を数える前に閲覧できるプロジェクトに絞ります。CLI と MCP のトークン認証でもリクエストごとに発行者の現在の所属を読み、指定された対象と突き合わせます。[権限の判定](../../src/core/operators/project-access.ts)・[トークンと機械クライアント](machine-access.md)

## 送信予定と会話の完了

操作で承認した返信には D1 の送信予定と outbox の試行が紐づきます。受信処理が人からの新しいメッセージを記録すると、同じトランザクションで未送信の予定を下書きに戻し、停止理由と元の承認者を出来事に残します。Queue の配送側は outbox の行を一度だけ取得します。配送が先に始まった場合は結果の確定を待ちます。

「送信して完了」の状態変更と完了時刻は、メールサービスが送信を受理してから保存します。解決アンケートはこの完了の出来事を受け取ります。

## 運営画面の遷移

受信箱・会話・課題・設定のリンクは `@barefootjs/router` を使います。遷移先の HTML が届くまで現在の画面を表示し、届いた時点で変更のある領域を更新します。運営者の認証情報が同じ間はサイドバーの要素が残り、ブラウザーの「戻る」「進む」も同じ経路を通ります。各画面のイベント購読や通信は、その画面を離れたときに解除します。

受信箱の行操作、会話の担当や状態の変更、拡張の切り替えには BarefootJS の `createMutation` を使います。保存後は `createQuery` でサーバーが確定した状態を読み、該当する行・カード・件数を更新します。送信時は元のフォームと同じ認可・確認を通り、移動済みの画面に届いた応答は破棄します。関連するブラウザテストでは、操作後も入力中の内容や周囲の要素が残ることを確認します。[ブラウザの読み取りと更新](../../src/browser/local-requests.js)

同じプロジェクトの公開記事は一覧と本文を領域更新で行き来できます。公開フォームや埋め込みチャットは、それぞれのドキュメントに設定した Content-Security-Policy を使います。
