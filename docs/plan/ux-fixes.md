# 使い勝手を場面の単位で直す

運営画面は、操作の一つひとつは動きますが、場面を通して使うと引っかかります。原因の多くは共通していて、**API の操作が、その形のままフォームとして画面に出ている**ことです。この文書は、ローカルの画面を実際に操作して見つけた問題と、直すための決まり、確かめ方を示します。

置き場所は `docs/plan/ux-fixes.md` です。goal には次の1文を渡します。

```
docs/plan/ux-fixes.md を読み、「通しの場面」のテストを先に書いてから、指摘をすべて直してください。「完了の条件」をすべて満たしたら完了です。
```

## 直すときの決まり

指摘に挙げていない画面にも、同じ決まりを当てはめます。

1. **人は ID を打たない。** 担当者、ラベル、記事、プロダクトは、候補から選ぶ。メールアドレス、記事 ID、プロダクト ID の手入力を、設定での新規登録以外から無くす。
2. **人は機械の単位を打たない。** 日時は日付で選ぶ。Unix ミリ秒のような値を画面に出さない。
3. **その場で使えない操作は出さない。** 問い合わせにフィードバック用の操作を出さない。完了した会話に、使えない返信欄を説明なしに出さない。
4. **よく使う操作は、対象のそばに置く。** 担当者とラベルは、会話の見出しの行で変える。折りたたみの中のフォームに入れない。
5. **操作のあとに、何が起きたかを伝える。** 送信、完了、保存のあとに、結果を1行で示す。
6. **一覧は、いま誰の番かを見分けられる。** 行のプレビューが、相手の文か、こちらの返信か、内部メモか、承認待ちの下書きかを区別する。
7. **有効にした機能は、使い始められる。** 拡張を有効にしたら、設定の場所、公開の URL、埋め込み方、動作の確かめ方に辿り着ける。
8. **ナビには、行き先のある項目だけを置く。** 設定ページの途中へ飛ぶだけの項目を置かない。

振る舞いの決まり(承認、内部メモは送られない、差出人は窓口から導く)と、`DESIGN.md`、層の決まりは変えません。

## 指摘

実際に操作して確かめたものです。重さの順に並べます。

### A. 信頼を壊すもの

| ID | 画面 | 起きていること | あるべき姿 |
|---|---|---|---|
| A1 | 会話の一覧 | エージェントが作った承認待ちの下書きがある会話(#5)で、行のプレビューに下書きの文が出る。「承認待ち」の印が無く、相手の文と見分けられない | 行に「承認待ち」を表示する。サイドバーに「承認待ち」の見出しと件数を置く |
| A2 | 会話の一覧 | プレビューが最後のメッセージをそのまま出す。内部メモ(#3)、送信済みの返信(#1)、相手の文が同じ見た目になる | プレビューの先頭に種別を示す(例: 「メモ:」「返信:」)。未対応の行では、相手の最後の文を優先する |
| A3 | 返信欄 | 「プレビュー」を押すと、入力した文が欄の下に見出しなしで繰り返されるだけ | 相手に届く形を示す。差出人、宛先、件名(`[#123]` 付き)、本文、添える記事を1つの枠で見せる |
| A4 | 会話の画面 | 問い合わせの「会話の詳細」に、フィードバック用の「確認済みにする」「問い合わせに変更」が出る | 会話の種類に合う操作だけを出す。押した場合の結果は未確認のため、テストで確かめる |
| A5 | 承認待ちの返信 | 操作が「承認して送信」だけで、直してから送れない | 承認の前に本文を編集できる。破棄もできる |
| A6 | 公開の画面 | 運営画面から、ヘルプページ、フィードバック、チャット、問い合わせフォームへ辿る手段が無い。拡張が「有効」でも、URL も埋め込み方も分からない | 拡張ごとに、公開の URL、埋め込み用のコード、プレビューへのリンクを示す |
| A7 | 存在しない URL | `404 Not Found` の文字だけが出る | 運営画面と公開の画面のそれぞれに、戻り先のある 404 を用意する |

### B. 使うたびに引っかかるもの

| ID | 画面 | 起きていること | あるべき姿 |
|---|---|---|---|
| B1 | 会話の画面 | 担当者を変えるには「その他の操作」を開き、メールアドレスを打って保存する | 見出しの行の担当者を押し、運営者の一覧から選ぶ。「自分が担当する」を1回で行える |
| B2 | 会話の画面 | ラベルは「会話の詳細」を開き、名前を打ち、「追加/削除」を選んで保存する | 見出しの行でラベルを選ぶ。既存のラベルを候補に出し、付いているものは押して外す |
| B3 | 会話の画面 | 記事を添えるには、記事 ID を打つ | 記事を題名で検索して選ぶ。返信欄から呼び出せる |
| B4 | 会話の画面 | 「会話の詳細」に、ラベル、フィードバック、ヘルプ記事、記事の候補のフォームが縦に並ぶ | 拡張のパネルは右の欄に置き、会話に関係するものだけを出す。初期状態で要約が見える |
| B5 | 会話の画面 | 送信しても、完了にしても、結果の知らせが無い。次の未対応へ進む手段も無い | 結果を1行で示す。「送信して完了」と「次の未対応へ」を用意する |
| B6 | 会話の画面 | 完了した会話は、返信欄が内部メモだけになる。理由の説明が無い | 「返信するには再開します」と示し、返信を書き始めたら再開する |
| B7 | 一覧の絞り込み | 担当者とラベルが自由入力。状態の選択肢に、フィードバック用の「受付済み」「確認済み」が混ざる | 担当者とラベルは候補から選ぶ。問い合わせとフィードバックを分ける |
| B8 | サイドバー | フィードバックの一覧への入口が無い。「すべて」で検索しないと見つからない | 受信箱と並べて「フィードバック」を置き、未確認の件数を示す |
| B9 | サイドバー | 拡張が8項目、同じアイコンで並ぶ。押すと、設定や拡張の管理のページの途中へ飛ぶ | 自分の画面を持つ拡張だけを置く。設定だけの拡張は、拡張の管理の中に置く |
| B10 | 対応状況の集計 | 一覧の下に折りたたみで置かれ、プロダクトは自由入力、期間は Unix ミリ秒で入力する | 独立した画面にする。プロダクトは選び、期間は「過去7日・30日・90日」と日付で選ぶ。初期状態で直近30日を表示する |
| B11 | 拡張の管理 | 16個が同じ見た目で並ぶ。何をする拡張かの説明も、設定の画面も、有効にしたあとの次の手順も無い | 1行の説明を付ける。有効なものと無効なものを分ける。設定と使い始め方へ進める |
| B12 | 設定 | プロダクト、運営者、保存期間、記事、書き出し、データの削除が1ページに並ぶ。記事の編集が設定の中にある | 項目ごとにページを分ける。記事は独立した画面にし、一覧・編集・プレビュー・公開を行える。データの削除は離して置く |
| B13 | 運営者 | 表示がメールアドレスだけ。一覧の担当者は頭文字1つ | 表示名を持てる。頭文字にはツールチップで名前を出す |

### C. 歩けていない場面

次の場面は確かめていません。同じ決まりで見直し、通しのテストで確かめてください。

- 公開の画面のすべて(ヘルプページ、フィードバック、チャット、問い合わせフォーム)。入口の URL が分からなかったため
- メールの受信から会話になるまで
- 無効になっている拡張(GitHub Issue、定型返信、スヌーズ、統合、振り分け、通知、迷惑メールの隔離)
- API トークンの発行と、CLI・MCP からの操作
- 幅 375px での表示と、キーボードだけでの操作
- 削除の確認、権限の変更、入力エラーの表示

## 通しの場面

次の場面を、Playwright の通しのテストとして先に書きます。テストは、ID やアドレスを打つ操作を含めません。含めないと書けない場面は、画面が決まりに反しています。

| ID | 場面 |
|---|---|
| J1 | 新しいメールが届く。一覧で見つけ、開き、自分を担当にし、ラベルを付け、プレビューで確かめて返信し、次の未対応へ進む |
| J2 | 相手から返事が届く。会話が未対応に戻る。返信して完了にする。完了した会話に、もう一度返事が届く |
| J3 | 送信に失敗した返信を一覧で見つけ、理由を読み、再送する |
| J4 | エージェントの下書きを一覧で見つけ、直してから承認して送る。別の下書きは破棄する |
| J5 | 記事を書き、プレビューし、公開する。公開のヘルプページで読める。会話の返信に、その記事を題名で探して添える |
| J6 | ユーザーがチャットに質問を書く。合う記事が示される。別の質問では問い合わせになり、番号が返る。その問い合わせが運営の一覧に出る |
| J7 | ユーザーがフィードバックを送る。運営のフィードバックの一覧に出る。確認済みにする。別の1件は問い合わせに変えて返信する |
| J8 | 会話から issue を起こす。内容を確かめてから起票する。issue が閉じると、知らせる下書きができ、承認して送る |
| J9 | 新しいプロダクトと窓口を登録する。拡張を1つ有効にし、示された手順だけで使い始める |
| J10 | 直近30日の数値を見る。プロダクトと期間を変える |
| J11 | 相手を指定してデータを削除する。確認の内容を読んでから実行する |

外部との通信(メール送信、GitHub、Workers AI)は、これまでと同じ手段で置き換えます。

## 歩いて確かめる

テストが通ったあと、運営者とユーザーの立場で、J1 から J11 をブラウザで実際に操作します。場面ごとに、操作の回数、迷った箇所、決まりに反する箇所を記録し、見つけたものを直します。直すものが無くなるまで繰り返します。

## レビュー用の成果物

- `docs/reports/ux/index.html`: 場面ごとに、手順の順に画面の画像を並べる。1つの場面を上から下へ見れば、流れが分かるようにする。
- `docs/reports/ux/README.md`: 指摘の ID ごとの対応、自分で見つけて直したこと、決まりに照らして判断に迷ったこと、直さなかったことと理由。

## 完了の条件

- 指摘 A と B が、すべて直っている。直さなかったものは、理由が書かれている。
- J1 から J11 のテストがあり、通っている。
- 運営画面のどの操作でも、設定での新規登録を除いて、ID・メールアドレス・機械の単位を手入力しない。これを検査するテストがある。
- C の場面を歩いた記録がある。
- `docs/plan/05-verification.md` のコマンドがすべて通る。
- レビュー用の成果物が揃っている。
