# 決まった段取りの受付(拡張 `flows`)

募集を開き、応募を受け、段階を進めながら、段階ごとの連絡を送る、という段取りを「流れ」として用意できるようにします。技術カンファレンスの運営で、スピーカーとスポンサーの対応に実際に使うことを前提にします。応募の受付、相手との連絡、進み具合の管理を、これ1つで行えることが目標です。

想定する規模は、1回の開催で、スピーカーの応募が100件弱、採択が20〜30人、スポンサーが50社、運営メンバーが10人です。

最優先で解くのは、次の2つです。返事が来ない相手を追いかける手間と、提出物が揃ったかどうかの管理です。画面の構成で迷ったら、この2つが楽になるほうを選びます。

## 段取りは、開催ごとに決める

段取りは、カンファレンスや勉強会によって違います。段階、連絡、依頼を、決め打ちにしません。

- 流れごとに、段階の名前・順番・分かれ道、段階ごとの連絡の文面、段階ごとの依頼を、運営者が画面で決められる。
- 同梱の見本(スピーカーの募集、スポンサーの募集)は、出発点として用意する。見本から作り、自由に書き換えられる。
- 既存の流れを複製して、新しい流れを作れる。前回の開催の段取りと文面を、次の開催に引き継ぐためである。複製するのは定義だけで、応募は引き継がない。
- 「辞退」「補欠」のような段階も、運営者が置ける。辞退が出たときの繰り上げは、自動では行わない。
- 応募がある流れの段階を変えるときは、影響する応募の件数を示し、消す段階にいる応募の移し先を尋ねる。

見本の段階は、次のとおりです。

```
スピーカーの募集:  応募 → 選考中 → 採択 → 日程の通知 → 事前の案内 → 当日の連絡 → 終了後
                                └→ 不採択
スポンサーの募集:  応募 → 審査中 → 承諾 → 請求の送付 → 入金の確認 → 掲載と提出物 → 当日の案内 → 終了後
                                └→ お断り
```

## 流れの定義

- 名前とプロジェクト(例: 「スピーカー募集 2027」)
- **受付のフォーム**: 項目(1行の文字、複数行の文字、選択、URL、ファイル)、必須かどうか、受付の開始と終了の日時、受付後に表示する文と送る文
- **段階**: 上のとおり
- **段階ごとの連絡**: その段階に進めたときに送る文面。送るかどうかは、進めるときに選ぶ
- **依頼**: 相手に出してもらうもの(例: 発表の概要、顔写真、ロゴ、請求先の情報)。依頼ごとに、締切と、出し方(返信に添える、専用のフォームから出す)を持つ。出たか、まだかを、相手ごとに持つ
- **依頼の条件**: 「このプランの相手だけ」のように、応募の項目の値で、依頼を出す相手を絞れる。スポンサーは、プランによって提出物が変わるためである

## 応募と会話

- 公開のフォームから応募があると、応募が1件でき、その相手との会話が1つ始まる。応募の内容は、会話の最初のメッセージとして見える。
- **フォームを通さずに、運営者が相手を流れに追加できる。** ゲストスピーカー、旅費を支援する学生、会場、業者のように、公募でない相手も同じ表で追えるようにする。
- 流れに載っている相手とも、通常の会話として個別のやりとりを続けられる。段階は、会話の状態(未対応、返信待ち、完了)とは別に持つ。
- 応募した相手には、流れの名前の目印が付く。

## 進み具合を見渡す

流れごとの画面が、この拡張の中心です。

- 段階ごとの人数を上部に並べ、その下に相手の表を出す。列は、相手、段階、項目の要点(題、プランなど)、最後のやりとり、**返事を待っている日数**、**まだ出ていない依頼**、担当者。
- 「返事を待っている日数が長い順」「未提出が多い順」「締切を過ぎた依頼がある」で、並べ替えと絞り込みができる。
- 相手を選んで、次の段階へ進める。進めるとき、段階の連絡を送るかを選ぶ。送る場合は、B の確認と承認を通る。
- **締切を過ぎた依頼の一覧**から、出ていない相手だけを選んで、催促の連絡を始められる。催促の文面には、その相手がまだ出していないものを差し込める。
- 突発の連絡(悪天候で搬入できない、など)を、段階と関係なく、流れの全員や一部にすぐ始められる。
- 段階を戻すこと、流れから外すこともできる。理由を残す。

## 送り間違いを防ぐ

- 確認の画面に、相手ごとの現在の段階を必ず出す。
- 文面が段階に結びついているとき、その段階にいない相手が宛先に入っていたら、送信を始めさせず、該当する相手と理由を示す。例: 採択の文面の宛先に、不採択の相手が入っている。
- 進める操作と、連絡の送信は、同じ確認の画面で行う。段階だけが進んで連絡が出ない、またはその逆を防ぐ。

## 確定した情報を、サイトで使えるようにする

提出物を受け取ったあと、サイトに掲載する作業の手間を減らします。掲載そのものは作りません。

- 流れごとに、公開してよい項目を、項目ごとに指定する(例: 名前、題、概要、顔写真、ロゴ、リンク先)。既定は、どの項目も非公開。
- 指定した段階(例: 採択、掲載と提出物)にいる相手の、公開してよい項目だけを、JSON とファイルの URL として取り出せる。取り出す口は、読み取り専用のトークンで守る。
- サイトの側は、ビルドのときにこれを読む。

## AI から使う

操作を、HTTP API・CLI・MCP に出します。選考は helpdesk の外で行う前提なので、データを取り出せることと、結果を戻せることが要ります。

- 流れと、応募の一覧を取り出す(段階、項目、依頼の状況、返事を待っている日数で絞り込める)。
- 応募の内容を、選考に使える形で取り出す。相手の名前や連絡先を伏せた形でも取り出せる。
- 選考の結果を、相手ごとの段階の変更として、まとめて反映する。反映の前に、変更の一覧を確認する。
- 条件に合う相手(例: 返事が7日来ていない、ロゴが未提出)への連絡の**下書き**を、相手ごとに作る。下書きは承認待ちに止まり、人が確認して承認するまで送られない。
- 応募の本文は、信頼できない入力として扱う。これまでの決まりと同じである。

## あとで足せるようにしておくもの

請求書の作成と入金の確認は、今回は人が行います。あとで請求書のサービスや銀行とつなぐ拡張を足せるよう、段階の移動と、依頼の受け取りを、出来事として記録し、ほかの拡張が受け取れるようにします。

## 作らないもの

- 請求書の作成、入金の照合。「請求の送付」は、ファイルを添えた連絡。「入金の確認」は、人が段階を進める操作。
- サイトへの掲載、日程表の作成と公開、チケットの販売、応募の公開と投票。
- 選考の採点の画面。
- 条件によって自動で段階が進む仕組み。段階は、人が進める。

## 型

```ts
type Flow = { id: FlowId; product: ProductId; name: string; form: FormDef; stages: Stage[]; requests: RequestDef[]; publicFields: FieldId[]; ... }
type Stage = { id: StageId; name: string; next: StageId[]; template?: TemplateId }
type RequestDef = { id: RequestId; name: string; stage: StageId; due?: Instant; via: 'reply' | 'form'; appliesWhen?: Condition }

type Application = {
  flow: FlowId
  conversation: ConversationNumber
  stage: StageId
  source: 'form' | 'operator'
  answers: Answers
  requests: Record<RequestId, { kind: 'pending' } | { kind: 'received'; at: Instant } | { kind: 'waived'; by: OperatorId }>
}

function advance(app: Application, to: StageId, flow: Flow): Result<Application, Rejected>
function validateFlow(flow: FlowDraft): Result<Flow, FlowError[]>   // no unreachable stage, no dangling `next`, exactly one entry stage
function requestsFor(app: Application, flow: Flow): RequestDef[]     // applies `appliesWhen`
function recipientsMismatch(template: TemplateId, apps: Application[], flow: Flow): Application[]  // who is not in the template's stage
```

## 自動で確かめること

- `validateFlow`: 正しい定義と、壊れた定義の例示。
- `advance`: 定義に無い移動を拒むこと。戻すこと。
- `requestsFor`: プランによって依頼が変わること。
- 流れの複製: 定義が写り、応募が写らないこと。
- 運営者が相手を追加した応募が、フォームからの応募と同じ表に出ること。
- 段階に結びついた文面を、別の段階の相手に送ろうとすると止まること。
- 締切を過ぎた依頼の一覧と、催促の宛先が合っていること。催促の文面に、相手ごとの未提出のものが入ること。
- 公開の取り出し口: 指定した段階と項目だけが出ること。非公開の項目、ほかの段階の相手が出ないこと。トークンが無いと読めないこと。
- MCP: 応募の取り出し、結果のまとめての反映、下書きの作成。下書きが、承認の前に送られないこと。
- フォーム: 必須の項目、受付の期間の外、ファイルの種類と大きさ、回数制限。
- 同梱の見本2つで、最初の段階から最後の段階までを通す。応募100件、スポンサー50社の例示データで、表の並べ替えと絞り込みが実用の速さで動くこと。
- `02-projects-and-roles.md` の権限: 流れ、応募、取り出しが、属していない運営者に見えないこと。
- 応募のデータが、相手単位の削除と、保存期間の対象になること。

## 完了の条件

- 流れの作成・編集・複製、公開のフォーム、運営者による追加、進み具合の表、段階を進める操作、催促、突発の連絡、公開の取り出し口、MCP の操作がある。
- 同梱の見本2つと、上の規模の例示データが、デモの環境に入っている。
- 検査が通っている。
- ハンズオンに、スピーカーの募集を、応募から終了後まで通す章と、未提出の相手に催促する章がある。
