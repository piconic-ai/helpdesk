# 段階2: 拡張の口を固める

性質の違う拡張を3つ作って、拡張の口の形を確かめます。同時に、操作を HTTP API・CLI・MCP に出します。

## 作る順番

1. **拡張の口**: `Extension` 型、登録、設定の検証、有効・無効、権限、拡張の migration。`helpdesk.config.ts`。
2. **出口の配送**: 出来事を outbox とキューで拡張へ届ける。再試行と、失敗の表示。
3. **`form`(入口)**: プロダクト内のフォームから問い合わせを受け、問い合わせ番号を返す。
4. **`canned`(操作と画面)**: 定型返信。相手の名前とプロダクト名を差し込む。
5. **`issues`(出口・操作・画面)**: 会話から issue を起こす。既存の issue に紐づける。issue が閉じたら、声を寄せた人への返信の下書きを作る。
6. **HTTP API**: 操作の一覧から作る。API トークンと権限の範囲。
7. **CLI と MCP**。
8. **口の見直し**: 3つの拡張を作って無理があった箇所を直し、`docs/dev/extensions.md` に口の説明を書く。

## 拡張の口

拡張は、次の1つの型で核に登録します。

```ts
type Extension = {
  id: ExtensionId
  permissions: Permission[]        // 'read_body' | 'send' | 'external_fetch'
  config: ZodSchema                // validated at startup
  intakes?: Intake[]               // entry: new routes that open conversations
  subscribers?: Subscriber[]       // exit: react to events
  operations?: Operation[]         // operation: appear in API, CLI and MCP automatically
  panels?: Panel[]                 // screen: fixed slots (beside a conversation, settings, list)
  migrations?: Migration[]         // its own tables, prefixed with its id
}
```

決まり:

- 有効にした拡張だけが動く。無効な拡張は、画面にも API にも CLI にも MCP にも現れない。
- 入口は、核が用意した「会話を開く」「メッセージを足す」手続きだけを通して書き込む。核のテーブルに直接書かない。
- 出口は、出来事を outbox とキューを通して受け取る。出口の失敗は、核の書き込みを失敗させない。再試行と、失敗の表示を核が持つ。
- 拡張が足した操作は、追加の作業なしに HTTP API・CLI・MCP に出る。
- 拡張の権限は宣言したものだけが使える。有効にするとき、運営者が権限を確認できる。
- 設定が検証に通らなければ、起動時に、どの項目がなぜ誤っているかを示して止まる。

2段階目の3つの拡張を作り終えたら、口の形を見直し、無理があれば変えます。3段階目に入ったあとは、口を変える前に、既存の拡張への影響を `docs/decisions.md` に書きます。

## AI から使う

- **操作の一覧**: 会話の一覧と取得、検索、返信の下書き、承認して送信、内部メモ、完了と再オープン、担当者、ラベル、迷惑メール、相手の過去の会話、設定の取得、書き出し、数値の取得。有効な拡張の操作がこれに加わる。
- **HTTP API**: 操作の一覧から機械的に作る。入力と出力のスキーマを公開する。
- **CLI**(`helpdesk`): HTTP API を呼ぶ薄い道具。`--json` で機械向けの出力を返す。終了コードと、標準出力・標準エラーの使い分けを守る。操作の一覧からコマンドを作り、コマンドごとの手書きを避ける。
- **MCP**: 操作の一覧からツールを作る。
- **安全**:
  - エージェントが作った返信は、既定で承認待ちに止まる。送信には運営者の承認が要る。
  - トークンは権限の範囲を持つ。読むだけ、下書きまで、という発行ができる。
  - メールの本文は、信頼できない入力として扱う。API と MCP の応答では、本文を他の項目と区別できる形で返し、本文の中の指示に従わないよう、ツールの説明に明記する。
  - 誰が、誰の代理で、何をしたかを、すべて記録する。

## 受け入れ条件

**拡張の口**

- 無効な拡張は、画面・HTTP API・CLI・MCP のどこにも現れず、その入口は 404 を返す。
- 拡張の設定が誤っていると、起動時に、どの項目がなぜ誤っているかを示して止まる。
- 出口が失敗しても、核の書き込みは成功する。失敗は運営画面に表示され、再試行される。
- 拡張が足した操作は、追加の実装なしに HTTP API・CLI・MCP から呼べる。
- 宣言していない権限を、拡張は使えない。
- `src/core/` が `src/extensions/` を読み込むと、層の検査が失敗する。

**`form`**

- 公開キーと許可した Origin からの送信が、そのプロダクトの会話になり、問い合わせ番号が返る。
- 許可していない Origin、誤った公開キー、回数制限を超えた送信は、会話にならない。
- 応答から、他人の会話の有無が分からない。

**`canned`**

- 定型返信を選ぶと、相手の名前とプロダクト名が入った下書きができる。下書きは、送信するまで相手に届かない。

**`issues`**

- 会話から issue を起こすと、運営者が確認した要約と問い合わせ番号だけが載る。相手の名前・アドレス・本文は載らない。
- 1つの issue に複数の会話を紐づけられ、運営画面で issue から元の会話を、会話から issue をたどれる。GitHub へのコメント投稿は行わない。
- issue が閉じると、紐づいた会話ごとに、知らせる返信の下書きができる。下書きは、運営者が承認するまで送られない。

**AI から使う**

- エージェントのトークンで MCP から、未対応の一覧を取り、1件に返信の下書きを付けられる。その返信は、運営者が承認するまで送信されない。
- 読むだけのトークンは、下書きを作れない。
- エージェントの操作は、代理した運営者と一緒に記録される。
- CLI は `--json` で機械向けの出力を返し、失敗時は 0 以外の終了コードを返す。

## 完了の条件

- 上の受け入れ条件が、すべて自動テストで確かめられている。
- `docs/dev/extensions.md` に、拡張の作り方が、最小の例と一緒に書かれている。
- `05-verification.md` のコマンドがすべて通る。
- 報告が `docs/reports/stage-2.md` にある。
