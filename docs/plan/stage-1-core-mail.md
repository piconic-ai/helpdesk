# 段階1: 核とメールで一切れ

核だけで、問い合わせの受信から完了までを通します。拡張の仕組みは、この段階では作りません。

## ゴール

> 窓口アドレス(例: `contact@slide.community`)にユーザーからメールが届く。運営者は運営画面の一覧でそれを見つけ、会話を開いて返信を書く。返信は窓口のアドレスを差出人として送られ、会話は「返信待ち」になる。ユーザーが返事をすると、同じ会話に入り「未対応」に戻る。運営者は内容を確認して「完了」にする。

## 作る順番

1. **土台**: `package.json`、`wrangler.jsonc`、`tsconfig.json`、Vite と Vitest の設定、oxfmt、cccc、層の検査、文書の検査、CI。`AGENTS.md` と `docs/dev/` を、slide のものを helpdesk に合わせて書き直して置く。`AGENTS.md` には `docs/plan/` への参照を入れる。`README.md` は短い説明と文書へのリンクだけにする。
2. **仕様**: `docs/features/f01-mail-conversation.md`。下の受け入れ条件を ID 付きで写し、遷移の24通りの表を含める。
3. **ドメインの型と遷移**: 型、`transition`、24通りの全数テスト。
4. **schema と store**: テーブル定義、migration、行を union に解析する store。矛盾した行を防ぐ CHECK 制約を付ける。解析できない行は握りつぶさず、エラーにする。
5. **受信**: Email Worker、キュー、解析、会話の判定、採番。
6. **運営画面(読む)**: Access の検証、運営者の登録、会話の一覧、会話の表示。
7. **返信**: 返信の操作、送信待ち、送信、成否の表示、失敗した返信の再送。
8. **さばく**: 完了、再オープン、迷惑メールにする・戻す、担当者、内部メモ、ラベル、検索、同じ相手の過去の会話。
9. **場を整える**: プロダクトと窓口アドレスの登録、運営者と権限、操作の記録の表示、相手単位の削除、保存期間。

操作は、最初から `operations/catalog.ts` に定義し、画面はそれを呼びます。段階2で、同じ定義を HTTP API・CLI・MCP に出すためです。

## 受け入れ条件

**受け取る**

- 登録した窓口アドレスに届いたメールが、そのプロダクトの会話として一覧に出る。
- 新しい会話に、重複しない問い合わせ番号が付く。同時に届いた2通にも、別の番号が付く。
- 2つのプロダクトの窓口に届いたメールは、それぞれのプロダクトの会話になる。
- 同じ相手が返信したメールは、`In-Reply-To` または `References` によって同じ会話に入る。
- 返信ヘッダーが欠けていても、件名の `[#123]` と差出人が一致すれば同じ会話に入る。
- 別の差出人が、他人の会話の `Message-ID` や番号を使って送ったメールは、新しい会話になる。
- 登録のない宛先へのメールは、会話にならない。
- 同じメールが2回配送されても、メッセージは1件しかできない。
- 解析に失敗したメールも、原文は R2 に残り、運営者が失敗に気づける。
- ISO-2022-JP と Shift_JIS のメールの件名と本文が、文字化けせずに表示される。

**読む**

- Access で認証されていない要求は、運営画面のどのページも見られない。
- 一覧は既定で「未対応」だけを表示し、状態・プロダクト・担当者・ラベルで絞り込める。
- 件名・差出人・本文で検索できる。
- 会話の画面から、同じ相手の過去の会話をたどれる。
- HTML メールの中の script は実行されず、外部の画像は読み込まれない。
- 添付は、ダウンロードとしてだけ取得できる。

**返信する**

- 返信すると、相手に届くメールの差出人は、その会話の窓口アドレスになる。
- 返信は、元のメールへの返信として並ぶヘッダー(`In-Reply-To`、`References`)と、件名の `[#123]` を持つ。
- 返信すると、会話は「返信待ち」になる。
- 送信に失敗した返信は「失敗」と表示され、再送できる。
- 送信の処理が2回走っても、相手に届くメールは1通である。
- 内部メモは、どの操作をしても相手に送られない。

**さばく**

- 相手から返事が来ると、「返信待ち」と「完了」の会話は「未対応」に戻る。
- 完了にした会話は、既定の一覧から消える。
- 会話に担当者を付けられ、担当者で絞り込める。
- 迷惑メールにした会話は、相手から返事が来ても「未対応」に戻らない。
- 自動応答とバウンスは、会話を「未対応」に戻さない。バウンスは、対応する返信を「失敗」にする。

**場を整える**

- 管理者は、プロダクトと窓口アドレスを登録できる。担当者は登録できない。
- 相手を指定して削除すると、その相手の会話、メッセージ、原文、添付が消える。
- 保存期間を設定すると、期間を過ぎた完了済みの会話の本文と添付が消える。設定しなければ消えない。

**記録**

- 会話の開始、受信、返信の送信と失敗、状態の変更、担当者の変更が、時刻と操作した人と一緒に `events` に残る。

## 完了の条件

- 上の受け入れ条件が、すべて自動テストで確かめられている。
- ローカルで、`.eml` を受信の入口に流し込み、画面で返信し、完了にするまでが通る。その手順が `docs/dev/development.md` に書かれている。
- `05-verification.md` のコマンドがすべて通る。
- 報告が `docs/reports/stage-1.md` にある。
