# 進め方

作業の刻み方、止まって確認する場合、報告の形式を示します。

## 作業の刻み方

- 機能ごとに、先に `docs/features/fNN-*.md` を slide の書式(利用場面、得られる結果、体験の流れ、作る範囲、作らないこと、受け入れ条件、未決事項)で書きます。受け入れ条件には `F01-AC1` の形の ID を付け、1つの条件に、外から観測できる結果を1つ書きます。仕様を書いたら、確認を待たずに実装へ進みます。
- 1つの commit は1つの動作またはリファクタリングに絞り、それを確かめるテストを含めます。
- 機能ごとにブランチを分け、`05-verification.md` の検証がすべて通ったら、自分で `main` に merge して次へ進みます。リモートが設定されていれば push し、PR を作ってから merge して構いません。
- まず細くても端から端まで動かし、あとから広げます。1段階目は、受信 → 一覧 → 返信 → 完了が通ることを最優先にします。
- 段階が終わるたびに、`04-workflow.md` の報告の形式で報告を `docs/reports/` に書き、次の段階へ進みます。
- 行き詰まったら、同じ手を繰り返さず、原因を切り分け、別の手段を選び、経緯を `docs/decisions.md` に残します。1つの拡張がどうしても進まないときは、その拡張を「未完」と記録して次へ進み、最後に戻ります。

文書は日本語、コードのコメントは英語で書きます。commit のメッセージは slide の履歴の書き方に合わせ、最終行に次の1行を入れます。

```
Co-authored-by: kfly8 <kentafly88@gmail.com>
```

GitHub の issue と PR を作る場合は、英語で書きます。依頼者への報告は丁寧な日本語で行います。

## 止まって確認する場合

次の場合だけ、作業を止めて依頼者に確認します。それ以外は自分で決めて進みます。

- 本番への deploy、DNS や Cloudflare アカウントの設定の変更、料金が発生する操作。
- 実在の相手へのメールの送信、実在のリポジトリへの issue の起票。
- リポジトリの公開範囲の変更、ライセンスの追加、パッケージの公開。
- 秘密の値(API キー、トークン)が必要になった。
- `00-overview.md` の「作らないもの」に手を入れないと進めない。
- Cloudflare の送信が、Workers から任意の宛先へ送れないなど、核が成り立たない制約が分かった。

## 報告の形式

段階ごとに、次を `docs/reports/` に日本語で書きます。

1. 満たした受け入れ条件の ID と、未完のもの。
2. 実行した検証コマンドと、その結果。
3. 自動で確かめたことと、人の確認として残したこと。
4. 自分で決めたこと(`docs/decisions.md` への参照)と、依頼者の判断があると良いこと。
5. 読んだ公式ドキュメントの URL。
