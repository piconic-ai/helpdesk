# 関連するヘルプ記事を、Clef で選んで示す

ユーザーが書いた内容に合うヘルプ記事を選び、その場で示します。選ぶ判断には、Workers AI の判断モデル Clef を使います。Clef は文章を作らず、問いに対する確率を返すだけなので、誤った説明を作って返す心配がありません。

置き場所は `docs/plan/ux-fixes-8.md` です。`ux-fixes-7.md` を済ませてから着手します。

実装の前に、Clef の現在の公式ドキュメント(`https://developers.cloudflare.com/workers-ai/models/clef` と `clef-flash` のページ、料金のページ)を読み、API の形、上限、料金を確かめてください。この文書の記述と違っていたら、公式の記述に従い、違いを `docs/decisions.md` に書きます。

## 1. 選び方

2段階で選びます。

1. **候補を絞る。** 質問の文で、公開中の記事を D1 の全文検索にかけ、上位20件までを候補にする。そのプロダクトの記事が20件以下なら、全件を候補にする。
2. **Clef に判断させる。** 候補の記事ごとに「この記事は、この質問の解決に役立つか」を `noul` の問いとして、1回の呼び出しにまとめて尋ねる。記事ごとの確率が返る。

```ts
const response = await env.AI.run('@cf/cloudflare/clef-flash', {
  model: 'clef-flash',
  state: {
    question,                                   // what the user wrote
    articles: candidates.map((a) => ({ id: a.id, title: a.title, summary: a.summary })),
  },
  questions: {
    ...Object.fromEntries(candidates.map((a) => [
      `article.${a.id}`,
      { type: 'noul', instructions: `Does the article with id "${a.id}" help resolve the user's question?` },
    ])),
    needs_human: {
      type: 'noul',
      instructions: 'Does resolving this require a person to look at the user\'s own account or data?',
    },
  },
})
```

決まり:

- **判断は純粋な関数に置く。** 確率の一覧としきい値から、示す記事を決める。既存の `decideChat(scores, threshold)` を広げる。モデルの呼び出しは `judge-client.ts` の1ファイルに閉じ込める。
- **示すのは、しきい値を超えた記事を、確率の高い順に3件まで。** 既定のしきい値は 0.6 とし、プロダクトごとに変えられる。超える記事が無ければ、記事を示さず、問い合わせへ進める。
- **人が見る必要のある質問は、記事で引き留めない。** `needs_human` の確率が高いときは、記事を示したうえで、問い合わせへの入口を先に出す。
- **記事には要約を持たせる。** 記事ごとに、200字ほどの要約の欄を足し、Clef には題と要約だけを渡す。要約が空なら、本文の先頭を使う。入力が長すぎると途中で切り捨てられるため、1回の呼び出しの入力を上限の半分以内に収める。
- **待たせない。** 呼び出しに時間の上限(1.5秒)を置く。超えたとき、失敗したときは、全文検索の上位を「関連しそうな記事」として示すか、そのまま問い合わせへ進める。判断の失敗で、問い合わせの受付を止めない。
- **モデルの使い分け。** ユーザーが待っている場面は `clef-flash`、待っていない場面(下の 2 の c と d)は `clef` を使う。モデルの名前は設定で変えられるようにする。
- **送るものを絞る。** Clef に渡すのは、質問の文と、記事の題と要約だけ。メールアドレスや名前は渡さない。拡張の権限に、外部への送信を宣言する。

記事が増えて全文検索では拾えなくなったら、候補を絞る段を、埋め込みによる検索(Vectorize)に差し替えます。今回は作りません。差し替えられるよう、候補を絞る処理を1つの関数にしておきます。

## 2. 示す場所

| | 場所 | いつ | 示し方 |
|---|---|---|---|
| a | ヘルプチャット(埋め込みと独立したページ) | 質問を送ったとき | 「関連する記事」として3件まで。そのあとに「解決した」「解決しなかった」 |
| b | 問い合わせフォーム | 送信を押したとき | 送る前に「この記事で解決しませんか」と示す。「このまま送る」を主ボタンにし、引き留めない |
| c | 自動の受付返信 | 問い合わせを受け付けたとき | 受付の文面の下に「関連しそうな記事」として添える。自動で選んだものであることを明記する。プロダクトごとに有効にする。既定は無効 |
| d | 運営の返信欄 | 会話を開いたとき | 「記事を添える」に、候補を先頭に並べる。合う記事が無いと判断したときは、「記事の候補に追加」を目立たせる |

a と b は、押すたびに呼び出します。入力の途中での提示(打つたびに候補が変わる)は、今回は作りません。

## 3. 記録と見直し

提示が役に立ったかを、出来事として残します。

- 提示: どの質問に、どの記事を、どの確率で示したか。示さなかった場合は、その旨と、いちばん高かった確率
- 反応: 記事を開いたか。「解決した」「解決しなかった」のどちらを選んだか。提示のあとに問い合わせになったか

これを使って、次を運営画面に出します。

- **対応状況の集計**: 待たずに解決できた割合(提示のうち「解決した」で終わった割合)
- **ヘルプ記事の一覧**: 記事ごとの、示された回数、開かれた回数、解決した割合。示されるのに解決しない記事は、直す候補として印を付ける
- **記事が無かった質問**: 提示できなかった質問の一覧。ここから記事を書き始められる

質問の文は、ユーザーが書いた内容そのものです。保存期間の対象にし、相手単位の削除で消えるようにします。

## 4. 日本語での確かさを測る

Clef が日本語の質問と記事をどの程度正しく結びつけるかは、公式のドキュメントに記載がありません。作る前に、測る手段を用意します。

- 例示データとして、質問と、合うはずの記事(または「合う記事なし」)の組を、30件以上用意する。言い換え、口語、誤字、複数の用件、記事と無関係な質問、人が見る必要のある質問を含める。
- 実際に Clef を呼び、しきい値ごとに、正しく示せた割合、誤って示した割合、示すべきなのに示さなかった割合を出すスクリプトを用意する。結果を `docs/reports/suggest-eval.md` に残す。
- このスクリプトは、Cloudflare のアカウントと料金が要るので、人が実行する。自動テストは、記録した応答を使って、判断の関数と画面の流れを確かめる。
- 誤って示す害(関係のない記事で引き留める)は、示さない害(そのまま問い合わせになる)より大きい。しきい値は、誤って示した割合が低くなる側に置く。

## 自動で確かめること

- 判断の関数: 確率の一覧としきい値の組み合わせを表にする。しきい値ちょうど、全件が下回る、4件以上が上回る、`needs_human` が高い、を含める。
- 候補が0件、1件、20件、21件以上のときの呼び出しの組み立て。問いの数が上限を超えないこと。
- 時間切れと失敗のとき、全文検索の結果か問い合わせへの導線に落ち、受付が止まらないこと。
- Clef に渡す内容に、メールアドレスと名前が含まれないこと。
- 質問の文に、指示を装った文章が入っていても、返るのが記事の一覧か問い合わせへの導線だけであること。
- a から d のそれぞれで、提示と反応が出来事として残ること。
- c が無効のプロダクトでは、受付返信に記事が添えられないこと。
- 相手単位の削除で、その相手の質問の記録が消えること。

- 4 の例示データと、測るスクリプトがある。実行は、人の確認として報告に残す。
- 「自動で確かめること」のテストがあり、通っている。
