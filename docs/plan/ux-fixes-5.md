# 余白の仕組み、課題の画面、ワークフローの確認

画面を操作して確かめた結果、直すべき点は3つに絞られます。部品どうしの間隔が仕組みとして決まっていないこと、課題の画面が情報を並べただけで整理されていないこと、ワークフローを端から端まで満たしているかを示す記録が無いことです。

置き場所は `docs/plan/ux-fixes-5.md` です。goal には次の1文を渡します。

```
docs/plan/ux-fixes-5.md を読み、1 から 4 をすべて反映してください。「完了の条件」をすべて満たしたら完了です。
```

これまでの決まり(`DESIGN.md`、層、振る舞い、これまでの `ux-fixes`)は変えません。

## 1. 余白を、個別の調整ではなく仕組みで決める

部品が隣どうしで接している箇所が、複数の画面にあります。1か所ずつ余白を足しても、次に作る画面でまた起きます。間隔を持つのは部品ではなく、部品を並べる側だと決めます。

### 決まり

- **部品は、自分の外側に余白を持たない。** カード、一覧、帯、ボタン、見出しは、margin を持たない。
- **間隔は、並べるための部品だけが持つ。** 次の4つを用意し、すべての画面をこれで組む。
  - `Stack`: 縦に並べる。間隔は `xs`・`sm`・`md`・`lg` から選ぶ。
  - `Cluster`: 横に並べ、折り返す。折り返したときも、行の間に同じ間隔が入る。
  - `Grid`: 格子に並べる。列の間と行の間に、同じ間隔が入る。
  - `PageBody`: ページの見出しと本文の間、区切りと区切りの間を `lg` にする。
- **使い分け**: 区切りと区切りの間は `lg`(24px)。カードとカードの間は `md`(16px)。カードの中の要素の間は `sm`(12px)。ラベルと入力欄の間は `xs`(8px)。
- **カードの内側の余白は1種類。** どのカードも同じ値にする。
- **折り返さない言葉を決める。** 問い合わせ番号、件数、日付、状態の名前、ボタンの文言は、途中で折り返さない。

### 接していた箇所

| 画面 | 接しているもの |
|---|---|
| 対応状況の集計 | 上段のカードと下段のカード。上段の3枚の高さも揃っていない |
| 対応状況の集計 | カードの補足の文と、説明のアイコン。アイコンだけが次の行に落ちる |
| 受信箱 | 行を選んだときに出る操作の帯と、一覧の最初の行 |
| 課題 | カードとカード |
| アカウント | 「アカウントを保存」のボタンと、その下のカード。保存のボタンが、入力欄より上に出ている |
| 会話 | 操作履歴の最後の行と、返信欄。「定型文を選ぶ」と、返信欄の上端 |
| 会話の関連情報 | 「この相手の問い合わせ」で、番号 `#14` が `#1` と `4` に折れる |
| 拡張の管理 | 区切りの見出しと、その下のカード |

### 自動で確かめること

- すべての画面を3つの幅で描画し、枠や背景を持つ要素どうしが、縦にも横にも 8px 未満で隣り合っていないことを検査する。
- 同じ行に並ぶカードの高さが揃っていることを検査する。
- 番号・件数・日付・状態の名前が、1行に収まっていることを検査する。
- 画面のファイルと部品のファイルに、margin の指定が無いことを検査する(並べるための4つの部品を除く)。

## 2. 課題の画面を、整理してから組み直す

いまの画面は、持っている情報をカードに順に流し込んでいます。題、プロダクト・状態・件数を点でつないだ1行、枠付きのリンク、枠のないリンク、割合の文、ボタンが、同じ強さで縦に並び、何を見て何をすればよいかが分かりません。

画面を組む前に、次の順で整理します。この手順は、ほかの画面を作るときにも使います。

1. **誰が、何のために開くかを1文で書く。**
2. **その人が知りたいことを、問いとして3つまで挙げる。**
3. **情報を、問いごとにまとめる。問いに答えない情報は、奥に置く。**
4. **問いに順位を付け、1番目をいちばん大きく、強く見せる。**
5. **同じ種類の情報は、同じ位置に、同じ形で繰り返す。揃える。**

### 課題の画面の整理

誰が、何のために: 運営者が、声をもとに何を直すかを決め、直したことを声の主に知らせるために開く。

問いは3つです。

1. **知らせるべき人が残っていないか。** 直したのに、まだ知らせていない声がある課題。
2. **次に何を直すか。** 開いている課題のうち、声が多いもの。
3. **直した効果があったか。** 直す前と後で、同じ原因の声が減ったか。

### 画面の構成

問いの順に、3つの区切りを縦に並べます。

```
課題                                                   [課題を追加]
声をもとに直すことを決め、直したら声の主に知らせます。

── 知らせる待ち  1 ─────────────────────────────────────────
  領収書の宛名を変更できるようにする           Slide
  2件の声のうち 1件にまだ知らせていません      [下書きを作る]

── 開いている  1 ─────────────────── 並び順: 声が多い順 ──
  課題                                 プロダクト   声    最初の声
  領収書の一括ダウンロード              Slide        1件   11時間前

── 直した  1 ──────────────────────────────────────────────
  課題                                 プロダクト   声    知らせた   直した後の声
  領収書の宛名を変更できるようにする     Slide        2件   1 / 2      1件(目安)
```

決まり:

- 「知らせる待ち」は、該当があるときだけ出し、画面のいちばん上に置く。主ボタンは、この区切りの「下書きを作る」だけにする。
- 「開いている」と「直した」は表にする。列の見出しを付け、数は右に寄せ、桁を揃える。
- 行を押すと、課題の詳細に移る。詳細に、紐づく声の一覧(番号、相手、ひとこと、知らせたかどうか)、GitHub の Issue へのリンク、効果の内訳を置く。一覧には、これらを出さない。
- 効果は、文ではなく数で示す。「直す前 30日: 1件 → 直した後 30日: 1件」のように件数を先に出し、割合は補足にする。件数が少ないときは「目安」と添える。直した後の期間が30日に満たないときは、何日ぶんかを示す。
- 課題の題が無いとき(`Inquiry #1` のような仮の名前)は、起票のときに題を必ず入れさせる。既存のものは、GitHub の Issue の題を取り込む。
- 検索と状態の絞り込みは、件数が20を超えるまで出さない。
- サイドバーの「課題」に、知らせる待ちの件数を出す。

### 会話の画面からの入口

- 「既存の Issue を選ぶ」が別の画面に移り、戻る先が受信箱になっている。会話の画面を離れず、関連情報のパネルの中で、題で探して選べるようにする。
- 関連情報のパネルの中で、ボタンの形が揃っていない(枠なし、枠あり、文字だけ)。主な操作1つを枠付き、ほかを控えめに、で統一する。

## 3. ワークフローを満たしているかを、記録で示す

5つのワークフローについて、手順ごとに「画面でできるか」「通しのテストがあるか」を1つの表にまとめ、`docs/reports/workflows.md` に置きます。レビューは、この表を見ます。

画面を操作して確かめた結果は次のとおりです。

| ワークフロー | 結果 | 確かめたこと | 直すこと・確かめていないこと |
|---|---|---|---|
| W1 問い合わせに答える | できる | 返信して完了、送信失敗の表示、承認待ちの下書き | 下の「W1 の指摘」。相手の返事で未対応に戻る流れは、画面からは確かめていない |
| W2 声を受け止める | できるが、引っかかる | 公開フォームから送ると、番号が返り、運営の「フィードバック」に出る。確認済みにできる | 下の「W2 の指摘」 |
| W3 自分で解決してもらう | できる | チャットに質問 → 記事の提示 → 「解決しなかった」→ 問い合わせ番号 → 運営の未対応に質問の文と一緒に出る | 記事の「役に立ちましたか」のあとの流れは確かめていない |
| W4 改善につなげる | 部品はあるが、流れとしてつながっていない | 課題の一覧、会話からの起票と紐づけの入口、声の集計 | 上の 2。起票、紐づけ、知らせる下書きから送信までは確かめていない |
| W5 場を整える | 確かめていない | — | プロダクトと窓口の登録、運営者の権限、保存期間、データの削除 |

### W1 の指摘

- 通常の「送信」と「送信して完了」で、毎回確認のダイアログが出る。いちばん多い操作なので、確認は挟まず、送信の直後に数秒だけ「取り消す」を出す。確認のダイアログは、エージェントや拡張が作った文を承認して送るときだけにする。
- 拡張が送ったメッセージの差出人が「拡張 issues」と、内部の名前で出る。拡張の表示名にする。
- 操作履歴に、担当者の変更・解除・変更が3行続く。短い時間の同じ種類の操作は、最後の状態の1行にまとめる。
- HTML メールの表示枠が固定の高さで、本文の下に大きな空白が残る。内容の高さに合わせる。
- 一覧で、差出人が長いとプロダクト名が「S…」と省略され、どのプロダクトか分からなくなる。プロダクト名は省略しない。

### W2 の指摘

- 公開のフィードバックで、連絡先のメールアドレスが必須になっている。空のまま送ると、何も起きず、理由も出ない。連絡先は任意にし、「任意」と示す。
- フィードバックを開いても、「確認済みにする」「問い合わせに変更」が画面に無く、「関連情報」のパネルを開かないと見つからない。この2つは、見出しの右の主な操作として出す。
- フィードバックの一覧の並び順が「待たせている順」になっている。返信を待たせていないので、「新しい順」「未確認を先に」にする。
- 一覧から、開かずに確認済みにできるようにする。

### そのほか

- 画面を移った直後、内容が薄い状態が見える時間が長い。切り替えのフェードが 150ms を超えていないか計測し、超えていれば直す。

## 4. ハンズオンを、実際の手順に合わせる

`docs/hands-on.md` を、いまの画面の文言と手順に合わせて更新します。章ごとに、対応するワークフローと通しのテストの ID を添えます。手順のとおりに操作する Playwright のテストを用意し、文書と画面がずれたら検査で分かるようにします。

## 完了の条件

- 1 の決まりで全画面が組まれ、「自動で確かめること」のテストが通っている。
- 課題の一覧と詳細が、2 の構成になっている。整理の手順(誰が・問い・まとめ・順位・揃え)を `DESIGN.md` に追記している。
- `docs/reports/workflows.md` に、5つのワークフローの手順ごとの表がある。すべての手順に、通しのテストがある。
- W1 と W2 の指摘がすべて直っている。
- ハンズオンが更新され、手順をなぞるテストが通っている。
- `docs/reports/ux-5/` に、全画面の変更前後の画像(3つの幅)がある。
- `docs/plan/05-verification.md` のコマンドがすべて通る。
