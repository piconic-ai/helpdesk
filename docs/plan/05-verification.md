# 検証

何を、どの手段で確かめるかと、人の確認として残すものを示します。

## 検証

自動テストに最大限投資します。人の確認は最小限にします。

```sh
pnpm format:check
pnpm build
pnpm exec tsc --noEmit
pnpm test:coverage
python3 scripts/check-docs.py
cccc .
```

| 対象 | 手段 |
|---|---|
| 遷移 | すべての組み合わせを `it.each` の表にする。必ず有効な結果か `Rejected` を返す |
| 会話の判定、採番、宛先の解決、自動送信の判別、チャットの判断、規則の評価 | Given-When-Then の例示。独立した軸が3つ以上なら表にする |
| 性質 | fast-check。例: 相手の返信のあと、迷惑メール以外の問い合わせは必ず `open`。`note` はどの操作の列でも送信されない。承認のない `sent` は作れない。エージェントの操作だけでは送信に至らない |
| 操作の列 | fast-check のモデルベーステスト。受信・返信・完了・再受信・統合・スヌーズの順序の組み合わせ |
| メールの解析 | `.eml` を例示データとして置く |
| store と入口 | ローカルの D1・R2・実際の HTTP を通す。置き換えるのは外部との通信(メール送信、GitHub、Workers AI、Webhook)だけ |
| 拡張の口 | 無効な拡張が、画面・API・CLI・MCP のどこにも現れないこと。出口が失敗しても核の書き込みが成功すること |
| 操作の一覧 | 画面・API・CLI・MCP が同じ操作の定義を通ること。権限の無いトークンが拒まれること |
| 画面 | Playwright。HTML メールの隔離は、外に出た request の有無で判定する |
| 層 | `scripts/layers.test.mjs` |

メールの例示には、次の意地悪な入力を含めます。

- 壊れた MIME、本文のないメール、巨大なヘッダー
- ISO-2022-JP、Shift_JIS、絵文字、サロゲートペア
- 改行を含む件名や差出人(ヘッダーの差し込み)
- HTML と script を含む本文、追跡用の画像
- 偽の `In-Reply-To`、他人の問い合わせ番号を書いた件名、自分の窓口のアドレスを差出人にしたメール
- 自動応答、バウンス、同じメールの再配送、受付返信どうしの往復
- 本文に、AI への指示を装った文章を含むメール

例示は、テストファイルではなくデータ(`*.examples.ts`)として置きます。自動化できない例には `manual: { reason }` を付け、「自動化されている」「理由付きで手動」のどちらでもない例がないことをテストで検査します。

基準:

- 関数の Cognitive Complexity は 15 以下。
- カバレッジの下限は、最初の計測値のすぐ下に置く。変更を通すために下げない。
- モックで成功させた結果を、実際の連携が動く根拠にしない。その確認が何を通しているかを報告に書く。
- 不具合を見つけたら、直す前に失敗するテストで再現する。
- 検査を通すために、検査や基準を緩めない。

## 人の確認として残すもの

次のものはローカルでは確かめられません。報告に「人の確認」として残し、確かめたように書かないでください。

- 実際の送信が相手に届くか。迷惑メールに入らないか。SPF・DKIM・DMARC の設定。
- Gmail、Outlook、iPhone のメールで、返信が元のメールに並んで見えるか。
- 本番の Email Routing、Queues、Access、Workers AI の設定と料金。
- ヘルプチャットの判断の、日本語での確かさ。
- 文言とデザインの良し悪し。
- セルフホストの手順を、作者以外の人が文書だけで最後まで進められるか。
